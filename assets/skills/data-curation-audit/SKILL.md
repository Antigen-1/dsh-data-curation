# 审阅与未决处置（data-curation-audit）

用于三件事：审已生成的核对结果、处置待裁定清单、给这类项目搭回归与故障注入夹具。
核心立场：**宁可留待裁定，也不制造"看起来已核实"的假象。**

## 一、审结果（按顺序，不跳）

1. `curation_status`：基线文件数、契约字段/通道、各通道提交量、接受/待裁定、最近落表。
2. `curation_verify`：逐检查项看 `pass / conditional / fail`，不要只看总结论。
3. 抽样复核（人做）：从接受格里按字段抽 5–10 格，回原材料核对页码/引用是否真的支持该值。抽到错 → 停止后续写入，查原因（目标锚定错？证据指向错？归一化过宽？）。
4. 看异议：状态库 `decision` 表（或 `curation_status` 输出）里 `dissent` 非空的格子，确认"多数"不是靠两个同源通道堆出来的。
5. 看待裁定原因分布：集中在 `missing_evidence` 说明采集阶段没记证据；集中在 `no_two_channel_agreement` 说明通道覆盖不足或材料质量差。

## 二、处置待裁定（禁止批量）

按 `pending.json` 分组，逐组决策，每条都要有理由与证据：

| 情形 | 处置 |
| --- | --- |
| 两个通道结果其实等价，只是没登记同义词 | 人确认后**改契约**（加同义词）→ 重签 → 重新比对 |
| 缺证据但值可信 | 补该格的页码/原文重新提交该通道，再裁定 |
| 通道覆盖不足 | 增加独立通道（如 OCR）后重新比对 |
| 材料本身模糊/矛盾 | 保持待裁定，报告里列明；需要时请人给出书面裁定 |
| 特例（业务上允许偏离口径） | 由人写明理由+证据+批准范围，记入例外清单；不得由工具自动生成 |

**不要**做的事：手工改工作区数据库（`.curation/project.sqlite` 的 `decision` / `ledger` 表）或 `pending.json`；调低 `minAcceptedRatio` 让验收变绿；把待裁定格在交付表里"顺手填上"；删掉 pending 文件当已处理。验收会按 run 存根与 ledger 对账，手改只会把 `decision_runs_recorded` / `ledger_complete` 打红。

## 三、回归与故障注入夹具

每个核对项目应沉淀一组夹具：**已知正确答案的合成记录** + **已知会出错的输入**。验收时要求：
- 错误样本必须被判为待裁定或有证据的失败；
- 合法样本不得被误报。

最小覆盖清单（对应插件的测试口径，项目可扩展）：

| 夹具 | 期望 |
| --- | --- |
| 一条记录含两个目标，字段属于非目标 | 不得把非目标值填给目标字段 |
| 单位不一致（1.2cm vs 12mm） | 归一化后一致，接受 |
| 中文数量词（两处 vs 2处） | 归一化后一致，接受 |
| 两通道都说"未提供" | 接受空白（允许空白的字段） |
| 一通道说"未提供"、另一通道有值 | 待裁定 |
| 视觉通道标 uncertain | 不计入有效票 |
| 部分闭合 vs 完全闭合 | 不得被同义词合并 |
| 术中出血 vs 术后出血 | 不得合并 |
| 三通道各说各话 | `competing_majorities` |
| 接受格缺页码/引用 | `missing_evidence` |
| 源文件被改一个字节 | `manifest_intact` fail，写入被阻断 |
| 交付表被手工改过 | `delivery_matches` fail |
| 记录键在 curated 表里还没有行 | 落表按键建行（upsert），不报错 |
| 同一通道同一批重提 | 替换旧值，不产生第二票 |

夹具要求：合成数据（禁止真实个人信息）、固定随机种子、可重复；每个夹具写清"期望判定 + 为什么"。

## 四、写报告的纪律

- 数字只引用工具输出，不凭记忆。
- 必须写出：总格数、接受数、待裁定数及原因、验收状态、备份路径、异议摘要。
- 结论分三级：`PASS`（可交付）/ `CONDITIONAL`（有未决，需人决定）/ `FAIL`（不可交付）。不得用"基本完成"这类模糊表述替代。
- 提到具体格时用"记录键 + 字段名"，不要用行号（行号会随表变化失效）。
